Method. Real headless Chrome with WebGL on an Apple M4 Pro, the actual HTTP/WebSocket server, authenticated controls, compression, and the game's render loop. Both directions pass through ordered queues that add latency and jitter without reordering WebSocket messages. Each browser's acceleration, steering and drifting inputs are replayed independently through the authoritative physics at 60 Hz, including static wall collisions. The displayed position and camera are compared on every rendered frame. Frame statistics exclude the first half-second.

What changed. Fixed-duration numbered movement commands; acknowledgment only after the server simulates them; replay of all unacknowledged commands; presentation between simulation ticks; full precision for gameplay state. A regression test captures the old boost-timer rounding bug (server speed 520 versus guest 716). Movement credit and bounded command queues constrain client requests.

Additional checks. The deterministic suite covers 80/160 ms RTT, asymmetric delay, jitter, 300 ms upload/download stalls, uneven rendering, guest identity, immediate controls, respawns, reconnect replay, duplicate commands, match resets, and server movement limits. All 141 game tests pass.

Retained failure. An earlier run with concurrent benchmarks passed 11 of 12 cases. One client temporarily stalled and reached the 300 ms ping display cap; the exact cause was not established. This failure was not counted as a pass. The final isolated matrix above passed all 12 cases with no server scheduling gaps above 100 ms and no update gap above 83.7 ms. Scope. This proves the recorded driving and camera scenarios on the local test machine. It does not claim zero internet latency, flawless behavior on every GPU, or absence of legitimate server corrections from other players' impacts.
